# Streaming Data Engineering Interview Questions & Answers

> **Data Engineering Diaries** | Master 30+ Production Streaming Questions for Senior & Staff DE Interviews

---

## Category 1: Structured Streaming Fundamentals

### Q1: What is Apache Spark Structured Streaming, and how does it differ from Spark DStreams?
**Answer**:
Structured Streaming is Spark's SQL-based stream processing engine built on top of DataFrames and Datasets.
Key differences:
1. **API Abstraction**: DStreams used low-level RDD APIs; Structured Streaming uses high-level DataFrame/SQL APIs.
2. **Processing Model**: Structured Streaming treats continuous streams as an unbounded growing input table.
3. **Time Semantics**: DStreams operated strictly on *Processing Time*; Structured Streaming natively supports *Event Time* processing and out-of-order watermarking.
4. **Optimization**: Structured Streaming leverages Catalyst Optimizer and Tungsten code generation.

---

### Q2: What are the three Output Modes in Structured Streaming, and when should you use each?
**Answer**:
1. **`append` Mode (Default)**:
   - *Behavior*: Only new rows added to the result table since the last micro-batch are output to the sink.
   - *Use Case*: Stateless streams (filtering/parsing) or watermarked windowed aggregations after watermark boundary passes.
2. **`complete` Mode**:
   - *Behavior*: The entire updated result table is written to the sink on every micro-batch.
   - *Use Case*: Global or non-watermarked window aggregations (e.g. running total counts).
3. **`update` Mode**:
   - *Behavior*: Only rows updated or inserted in the result table since the last micro-batch are emitted.
   - *Use Case*: State updates, metric counters without rewriting unchanged rows.

---

### Q3: Why is Adaptive Query Execution (AQE) disabled for Structured Streaming?
**Answer**:
AQE dynamically changes the physical query execution plan (repartitioning shuffles, converting sort-merge joins to broadcast joins) mid-execution based on runtime partition statistics. In Structured Streaming, stateful operators (aggregations, joins, deduplication) rely on a stable, deterministic state memory layout across micro-batches. Changing the physical execution plan dynamically would break state compatibility across micro-batches.

## Category 2: Watermarking & Late Data Handling

### Q4: How does Watermarking work in Structured Streaming?
**Answer**:
A watermark defines the threshold of acceptable delay for late-arriving events relative to the maximum event time seen by Spark so far:
$$\text{Watermark} = \max(\text{EventTime}) - \text{AllowedDelay}$$
As events process through micro-batches:
1. Spark tracks the highest `event_time` seen across partitions.
2. Spark updates the global watermark boundary at the end of each micro-batch.
3. Any arriving record with `event_time < watermark` is dropped from stateful calculations.
4. Windows older than the watermark threshold are evicted from the StateStore, freeing memory.

---

### Q5: Can you use Watermarking without an Output Mode?
**Answer**:
No. Watermarking is meaningful primarily in stateful queries (`groupBy`, `window`, `dropDuplicates`, stream-stream joins). It enables `append` mode for stateful queries by signaling when a time window is closed and safe to emit.

## Category 3: Checkpointing & Exactly-Once Semantics

### Q6: How does Structured Streaming guarantee Exactly-Once processing?
**Answer**:
Exactly-once processing requires three components working in tandem:
1. **Replayable Source**: Source (like Kafka or File storage) must allow re-reading specific offset ranges on failure.
2. **Checkpointing & Write-Ahead Log**: Spark stores consumed offsets and state snapshots in `/checkpointLocation/offsets/` and `/checkpointLocation/state/`.
3. **Idempotent / Atomic Sink**: Destination sink (like Delta Lake) must support atomic commits so micro-batch re-execution writes identically without creating duplicate data.

---

### Q7: What files are stored inside a streaming Checkpoint directory?
**Answer**:
- `offsets/`: Directory containing offset metadata for each micro-batch (e.g. `0`, `1`, `2`).
- `commits/`: Directory recording successfully committed micro-batch IDs.
- `state/`: Delta files generated by stateful operators (RocksDB / HDFSBacked StateStore).
- `metadata`: Global stream metadata JSON defining query schema GUID and run configuration.

## Category 4: Stream Joins & Stateful Operations

### Q8: What are the constraints for performing Stream-to-Stream Outer Joins?
**Answer**:
Stream-to-stream outer joins (Left/Right/Full Outer) require:
1. **Watermarks on BOTH streams**: Both DataFrames must have `withWatermark()` defined.
2. **Time Range Condition**: A time condition constraining how far apart in event time the join keys can arrive (e.g. `click_time BETWEEN imp_time AND imp_time + INTERVAL 10 MINUTES`).
This allows Spark to determine when unmatched records will never receive a join match and can be evicted from memory.

---

### Q9: What is the difference between HDFSBackedStateStore and RocksDBStateStoreProvider?
**Answer**:
- **HDFSBackedStateStore**: Stores state in JVM Heap memory. Prone to severe Java Garbage Collection (GC) pauses and OutOfMemory errors when scaling to millions of state keys.
- **RocksDBStateStoreProvider**: Stores state off-heap in native memory and local SSD disk storage. Scales efficiently to billions of keys with minimal GC overhead.

---

## Category 5: Performance Tuning & Delta Lake

### Q10: How do you tune `spark.sql.shuffle.partitions` for Structured Streaming?
**Answer**:
The default value of 200 is designed for large batch ETL queries. For streaming queries processing small micro-batches, 200 shuffle partitions creates 200 tiny tasks per micro-batch, causing scheduling overhead latency.
*Rule of thumb*: Set `spark.sql.shuffle.partitions` to 2x the number of Kafka topic partitions (e.g. 10 partitions → 20 shuffle partitions).

## Category 6: Triggers, Late Data, Joins & Production Operations

### Q11: Compare the Structured Streaming trigger types (`processingTime`, `once`, `availableNow`, `continuous`).
**Answer**:
- **`processingTime="10 seconds"`**: Runs micro-batches on a fixed cadence.
- **`availableNow=True` (replaces deprecated `once=True`)**: Processes all currently queued backlog data across multiple bounded micro-batches (respecting `maxOffsetsPerTrigger`) and stops cleanly—ideal for cost-efficient scheduled incremental jobs on Airflow/Databricks.
- **`continuous="1 second"`**: Experimental low-latency (~1 ms) epoch-based engine supporting only stateless map/filter ops.

---

### Q12: How do `maxOffsetsPerTrigger` (Kafka) and `maxFilesPerTrigger` (Files) protect streaming clusters?
**Answer**:
After an outage or backlog spike, an unbounded first micro-batch might pull 500M messages and OOM executors. Setting `maxOffsetsPerTrigger` caps each micro-batch size so the stream drains backlogs smoothly across steady batches without blowing heap memory.

---

### Q13: How does `dropDuplicates(["event_id"])` work in Structured Streaming with vs. without a watermark?
**Answer**:
- **Without watermark:** Spark retains **every** seen `event_id` in StateStore forever—eventually exhausting cluster memory/disk.
- **With `.withWatermark("event_ts", "1 hour").dropDuplicates(["event_id", "event_ts"])`:** Spark bounds state retention to the watermark window and safely evicts old keys.

---

### Q14: How do you handle Stream-to-Static Dimension Joins when the static lookup table updates hourly?
**Answer**:
Standard `stream_df.join(static_df)` caches the static table plan at stream startup or re-reads it every micro-batch depending on source. For Delta Lake targets, Spark automatically picks up new Delta snapshot versions on each micro-batch; for JDBC/external lookups, refresh inside `foreachBatch()` or broadcast on a periodic TTL cache.

---

### Q15: Explain `foreachBatch()` and why idempotency inside it is non-negotiable.
**Answer**:
`foreachBatch(fn)` gives you each micro-batch as a standard static DataFrame (`batch_df, batch_id`) so you can run Delta `MERGE INTO`, multi-sink writes, or JDBC upserts. Because Structured Streaming provides **at-least-once** delivery into `foreachBatch()` on failure recovery, your function must be idempotent (e.g., key writes by `batch_id` or Delta `txnAppId`/`txnVersion`, or use `MERGE`).

---

### Q16: What is Arbitrary Stateful Processing (`flatMapGroupsWithState` / `applyInPandasWithState`), and when is it needed?
**Answer**:
Built-in `window()` handles fixed/sliding aggregations, but sessionization with dynamic inactivity timeouts, complex fraud state machines, or funnel tracking across irregular events requires `applyInPandasWithState` / `flatMapGroupsWithState` with explicit state structs and `GroupStateTimeout` eviction.

---

### Q17: Why must you NEVER change certain streaming query topologies while reusing an old checkpoint?
**Answer**:
The checkpoint `state/` directory binds to exact stateful operator IDs, key schemas, and `spark.sql.shuffle.partitions`. Changing grouping keys, adding/removing stateful operators, or altering `shuffle.partitions` breaks checkpoint deserialization—requiring a new checkpoint directory and coordinated cutover.

---

### Q18: How do you perform streaming writes into multiple downstream sinks (e.g., Bronze Delta + Alert Kafka) atomically?
**Answer**:
Use `foreachBatch()`, `.persist()` `batch_df` so Spark computes transformations once instead of twice, write to both sinks inside the function, and `.unpersist()` in a `finally` block.

---

### Q19: How do you handle late-arriving events that exceed the Watermark instead of silently dropping them?
**Answer**:
If business SLAs require capturing ultra-late arrivals (e.g., mobile offline syncs arriving 48 hours late), keep a tight watermark (1–2 hours) on the real-time Gold stream for low latency, and run an hourly/daily batch backfill or Delta `MERGE` from the raw Bronze table (which retains all events regardless of lateness).

---

### Q20: Explain Sliding Window vs. Tumbling Window vs. Session Window.
**Answer**:
- **Tumbling (`window("ts", "5 minutes")`)**: Non-overlapping fixed buckets.
- **Sliding (`window("ts", "10 minutes", "5 minutes")`)**: Overlapping buckets; each event belongs to multiple windows.
- **Session (`session_window("ts", "15 minutes")`)**: Dynamic activity windows that stay open until a gap of inactivity exceeds 15 minutes.

---

### Q21: How do you monitor streaming health in production?
**Answer**:
Attach a `StreamingQueryListener` (`onQueryProgress`) to emit `inputRowsPerSecond`, `processedRowsPerSecond`, `batchDuration`, `watermark`, and `stateOperators.numRowsTotal` to Prometheus/Datadog. Alert whenever `processedRowsPerSecond < inputRowsPerSecond` (growing lag) or StateStore memory climbs unboundedly.

---

### Q22: What is the difference between `startingOffsets="earliest"` vs `"latest"` in Kafka Structured Streaming?
**Answer**:
`startingOffsets` applies **only when starting a fresh checkpoint**; once offsets exist in `/checkpoint/offsets/`, Spark always resumes from the checkpointed offsets. Use `failOnDataLoss=false` cautiously if Kafka retention expires older offsets during long outages.

---

### Q23: How does RocksDB StateStore prevent JVM GC pauses in stateful streaming?
**Answer**:
JVM Heap StateStore stores millions of Java HashMap entries on-heap, triggering multi-second Stop-the-World GC pauses. RocksDB manages state in native C++ off-heap memory + local SSD SST files, keeping JVM heap tiny and GC latency flat.

---

### Q24: What happens if a Delta Lake streaming sink receives concurrent writes from another batch `UPDATE`/`OPTIMIZE` job?
**Answer**:
Non-conflicting `OPTIMIZE` compaction works seamlessly with streaming appends via Delta OCC (and Deletion Vectors). However, concurrent batch `UPDATE`/`DELETE` modifying rows in the same files can trigger `ConcurrentDeleteReadException` unless operations target disjoint partitions (`replaceWhere`).

---

### Q25: How do you handle schema evolution of JSON payloads arriving from Kafka in Structured Streaming?
**Answer**:
Never use `from_json()` with an unversioned hardcoded schema if producers evolve freely. Pair Kafka messages with **Confluent Schema Registry (Avro/Protobuf)**, or ingest raw JSON strings into Bronze and parse columns + `_rescued_data` in Silver so malformed payloads never crash the streaming query.

---

### Q26: How do you gracefully stop and restart a Structured Streaming job for code deployments?
**Answer**:
Trigger a graceful stop via `query.stop()` (or cluster shutdown hook) so the in-flight micro-batch finishes committing offsets before termination, deploy the new artifact, and restart against the same durable checkpoint path.

---

### Q27: Why do Stream-Stream Inner Joins also benefit from Watermarks + Time Range conditions even though they aren't Outer Joins?
**Answer**:
Without watermarks and time bounds on both sides of an inner stream-stream join, Spark must buffer **100% of past events from both streams forever** because a late event could theoretically match an event from 6 months ago—causing inevitable StateStore OOM.

---

### Q28: How do you test Spark Structured Streaming pipelines reliably in pytest?
**Answer**:
Use `MemoryStream` (or write batches to a temp JSON/Parquet directory with `availableNow=True` / `processAllAvailable()`), feed out-of-order timestamps to verify watermark eviction, and query the resulting Delta/memory sink deterministically.

---

### Q29: What is the Small Files Problem in Streaming Sinks, and how do you solve it?
**Answer**:
A 5-second micro-batch writing 100 KB per partition creates 17,280 tiny files per day. Fix by widening trigger intervals (`1–5 minutes`), enabling `delta.autoOptimize.optimizeWrite` / `autoCompact`, or scheduling async `OPTIMIZE` compaction.

---

### Q30: How do you achieve end-to-end low latency when writing streaming aggregations to an operational dashboard?
**Answer**:
Use `update` output mode inside `foreachBatch()` to upsert only changed window buckets into a fast key-value/OLTP store (Redis, DynamoDB, PostgreSQL) or Snowflake Dynamic Tables / Databricks SQL Serverless over Delta Lake.
